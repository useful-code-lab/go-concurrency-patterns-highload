# Алгоритмы конкурентной работы

## Система управления электронной очередью в Банке
ТЗ: «Система распределенного обслуживания в многопрофильном банке»
1. Цель
Реализовать масштабируемый алгоритм конкурентности (Dispatcher Pattern), который распределяет клиентов по специализированным окнам обслуживания, используя личные каналы связи между менеджером и сотрудниками.
2. Сущности и структуры данных (Models)
ServiceType (Тип услуги):
Тип: перечисление (строковые константы).
Варианты: Кредиты, Депозиты.
Client (Задача):
Поля: ID (int), Name (string), Request (ServiceType).
Specialist (Воркер):
Поля: ID (int), Specialty (ServiceType).
Каналы:
Window (chan Client) — личный входящий канал.
ReadyBoard (chan chan Client) — ссылка на общее табло готовности.
Quit (chan bool) — сигнал на завершение работы.
Зависимость: Ссылка на sync.WaitGroup для контроля завершения.
BankManager (Диспетчер):
Поля:
GlobalQueue (chan Client) — общая входящая очередь.
Boards (map[ServiceType]chan chan Client) — карта табло для разных специальностей.
Employees — слайс (список) всех созданных специалистов.
Зависимость: Свой экземпляр sync.WaitGroup.
3. Алгоритм работы (Business Logic)
А. Жизненный цикл Специалиста (метод Work):
Запускается в отдельной горутине.
В бесконечном цикле первым делом отправляет свой канал Window в ReadyBoard.
Через select ожидает либо появления Client в Window, либо сигнала в Quit.
При получении клиента: имитирует работу (time.Sleep) и выводит отчет в консоль.
При получении Quit: выходит из цикла и уменьшает счетчик WaitGroup.
Б. Работа Менеджера (метод Run):
Запускает фоновую горутину для распределения.
Читает клиентов из GlobalQueue через for range.
Для каждого клиента находит нужное табло в map.
Блокируется, пока на этом табло не появится свободное окно: freeWindow := <-board.
Передает клиента по ссылке: freeWindow <- client.
После закрытия GlobalQueue рассылает всем специалистам сигнал в их каналы Quit.
4. Проверка и запуск (Main)
Создать канал GlobalQueue.
Инициализировать BankManager.
Нанять (создать и запустить) минимум 3 специалистов (например: 2 по кредитам, 1 по депозитам).
Запустить Менеджера (Run).
В цикле отправить 10-15 клиентов с разными типами запросов.
Закрыть GlobalQueue (close).
Вызвать метод ожидания (Wait), чтобы программа не завершилась раньше воркеров.
Решение задачи в файле: ``cmd/bank_queue/bank_queue.go``

# Конкурентный ограничитель запросов (Rate Limiter)
Техническое задание: Rate Limiter (Token Bucket)
1. Цель
Реализовать механизм управления потоком задач, который гарантирует выполнение не более 
 операций за период времени 
. Система должна быть потокобезопасной и поддерживать корректную остановку.
2. Входные параметры
Rate (
): Количество доступных "токенов" (разрешений на выполнение) за период.
Period (
): Временной интервал (например, 1 секунда).
Task Queue: Буферизированный канал задач.
Context: Сигнал для отмены и завершения работы.
3. Алгоритм работы (Текстовая модель)
Алгоритм строится на принципе "Корзины токенов" (Token Bucket), но адаптированном под событийную модель Go:
Инициализация ресурсов:
Создать канал задач (tasks).
Настроить тикер (time.Ticker), который срабатывает каждые 
 единиц времени. Это обеспечит равномерное распределение задач внутри периода.
Основной цикл обработки (Run):
Запустить бесконечный цикл select, который ожидает одного из трёх событий:
Событие А: Сработал тикер (Разрешение получено).
Проверить, есть ли в канале tasks ожидающая задача.
Если есть — извлечь задачу и запустить её в отдельной горутине (чтобы выполнение самой задачи не блокировало планировщик).
Если задач нет — просто ждать следующего тика.
Событие Б: Контекст закрыт (ctx.Done()).
Остановить тикер.
Прекратить чтение из каналов.
Завершить выполнение функции Run.
Событие В (Опционально): Переполнение очереди.
Если канал tasks полон, метод AddTask должен либо блокироваться, либо возвращать ошибку (в зависимости от требований к надежности).
Масштабирование (Concurrency):
Для того чтобы "воркеры" не простаивали, если сама задача тяжелая, их запуск должен быть неблокирующим. Однако общее количество одновременно выполняющихся задач также может быть ограничено (например, через Semaphore или WaitGroup).
4. Визуализация логики
mermaid
graph TD
    A[Начало: Run] --> B{Ждать событие}
    B -- Тик таймера --> C{Есть задачи в очереди?}
    C -- Да --> D[Запустить задачу в горутине]
    D --> B
    C -- Нет --> B
    B -- ctx.Done --> E[Остановка и выход]
Используйте код с осторожностью.

5. Требования к реализации (Check-list)
Используется time.NewTicker для генерации интервалов.
Тикер обязательно освобождается через defer ticker.Stop().
Задачи выполняются асинхронно, чтобы Slow Task не сдвигала тайминг следующей задачи.
Реализована защита от "паники" (если функция задачи пустая).
Решение задачи в файле ``cmd/tb_rate_limiter/tb_rate_limiter.go``


## Техническое задание: Универсальный Мультиплексор (Fan-in)
1. Входные данные и инициализация
Типизация: Использовать Generics, чтобы алгоритм работал с любым типом данных.
Параметры: Функция должна принимать context.Context (для внешнего управления жизненным циклом) и вариативный список каналов-источников ...<-chan T.
Создание шины: Инициализировать результирующий канал resultCh.
2. Управление жизненным циклом (Оркестрация)
Счетчик активных каналов: Создать sync.WaitGroup для отслеживания работающих горутин-воркеров.
Регистрация: Установить счетчик wg.Add(len(sources)), равный количеству входящих каналов.
3. Алгоритм работы воркера (Multiplexing Logic)
Для каждого входящего канала запустить отдельную горутину, которая выполняет следующий цикл:
Слушание событий: Использовать оператор select для мониторинга двух событий:
Событие «Сигнал отмены»: Если ctx.Done(), немедленно прекратить работу воркера.
Событие «Данные в канале»: Попытаться прочитать значение из входящего канала.
Проверка закрытия: Если входящий канал закрыт (ok == false), воркер должен уменьшить счетчик wg.Done() и завершить работу.
Пересылка данных: Полученное значение нужно отправить в результирующий канал resultCh.
Важно: Отправка также должна быть внутри select с проверкой ctx.Done(), чтобы воркер не заблокировался навсегда, если основной потребитель перестал читать.
4. Корректное завершение (Cleanup)
Мониторинг завершения: Запустить отдельную фоновую горутину («Наблюдатель»), которая будет ждать выполнения wg.Wait().
Закрытие выхода: Как только все воркеры отработали (все каналы закрыты или контекст отменен), «Наблюдатель» обязан закрыть канал resultCh.
Это предотвращает deadlock и позволяет потребителю выйти из цикла for range.
5. Обработка краевых случаев (Edge Cases)
Пустой список: Если на вход не подано ни одного канала, функция должна вернуть уже закрытый канал (или сразу закрыть его), чтобы не блокировать потребителя.
Nil-каналы: Игнорировать или обрабатывать nil каналы, чтобы не вызвать вечную блокировку в select.
Резюме потока данных:
Input: Ch1, Ch2, Ch3 + Context.
Process: 3 горутины копируют данные в MainCh.
Control: WaitGroup следит за окончанием.
Output: Единственный MainCh, который закроется сам, когда все источники иссякнут.
Решение задачи в файле ``/cmd/multiplex_fan_in/multiplex_fan_in.go``


## Алгоритм Fan-out (веерная рассылка)
Паттерн Fan-Out в Go используется для распределения задач из одного канала между несколькими горутинами-воркерами. Это позволяет параллельно обрабатывать данные и максимально эффективно использовать CPU.
1. Подготовка структуры данных
Определите, какие данные вы будете передавать. Это может быть struct с полями для входных данных и метаинформацией.
Совет: Если планируете возвращать результаты, сразу продумайте структуру для ответа. 
2. Создание канала задач (Jobs Channel)
Создайте канал, через который «продюсер» будет передавать работу «воркерам».
Буферизация: Используйте буферизированный канал make(chan Task, bufferSize), чтобы продюсер не блокировался сразу, если воркеры заняты.
Закрытие: Продюсер обязан закрыть канал (close(jobs)), когда задачи закончатся. Это критический сигнал для воркеров, чтобы они могли корректно завершить циклы range. 
3. Инициализация синхронизации (WaitGroup)
Объявите var wg sync.WaitGroup. Она нужна, чтобы основной поток программы дождался завершения всех запущенных воркеров. 
Для каждого воркера делайте wg.Add(1) перед запуском горутины.
Внутри воркера используйте defer wg.Done().
4. Запуск пула воркеров (Worker Pool)
В цикле for запустите нужное количество горутин (например, 5 или по количеству ядер CPU). 
Каждая горутина должна в цикле for task := range jobs читать из общего канала.
Особенность Go: Планировщик сам распределит задачи — одно сообщение из канала получит ровно один свободный воркер. 
5. Обработка данных внутри воркера
Внутри цикла воркера опишите логику обработки.
Fan-In (опционально): Если нужно собирать результаты, воркеры должны отправлять итоги в другой общий канал results.
Контроль отмены: Рекомендуется передавать в воркер context.Context, чтобы можно было прервать работу при таймауте или ошибке. 
6. Финализация (Wait)
В основной горутине после отправки всех задач и закрытия канала вызовите wg.Wait(). 
Это гарантирует, что программа не завершится, пока последний воркер не доделает свою задачу.
